# BloomPath Grounded QA Service

BloomPath is a Micronaut/Kotlin service for answering operational questions over a seeded frontline-services database. It turns natural language into a structured intent, executes read-only parameterized SQL against H2, derives record provenance from JDBC metadata and primary keys, and formats an answer from retrieved rows.

The current repository is an Ollama-backed proof of concept using `gemma4:e4b-mlx`. It does not contain an OpenAI `gpt-4o-mini` client or an `OPENAI_API_KEY` binding. Provenance is generated by application code, so record IDs are not LLM-generated or hallucinated.

## System Overview & Core Capabilities

The API exposes `POST /api/v1/query` and supports:

- `SUCCESS`: an answerable question with grounded answer text and provenance;
- `AMBIGUOUS`: multiple matching entities and a clarification prompt;
- `REFUSED`: an out-of-scope question, such as a financial or budget request.

The pipeline uses structured intent parsing, parameterized SQL, startup schema/seed loading, JDBC-derived record provenance, and answer synthesis constrained to retrieved database rows. Ordinary-row provenance comes from source-table primary keys found through JDBC metadata. Aggregate provenance comes from a contributor query that identifies the rows behind the aggregate.

## Architecture & Pipeline Breakdown

The source packages are:

```text
ai.bloompath
├── Application.kt
├── ai/{AiDtos.kt, AnswerSynthesisService.kt, IntentParserService.kt}
├── config/DatabaseInitializer.kt
├── controller/QueryController.kt
├── dto/{QueryRequest.kt, QueryResponse.kt}
└── service/{DatabaseQueryService.kt, ProvenanceService.kt, QaEngineService.kt}
```

1. **Natural-language intent parsing.** `IntentParserService` is a Micronaut `@AiService`. It returns `IntentDecision` with `IntentAction.EXECUTE`, `AMBIGUOUS`, or `REFUSE`. An executable decision contains one read-only SQL statement with `?` placeholders and an ordered parameter list. The prompt requires every executable query to select a source primary key, including aggregate queries.
2. **Parameterized SQL execution.** `QaEngineService` passes executable decisions to `DatabaseQueryService`, which binds values to a `PreparedStatement` and snapshots rows/column metadata into `QuerySnapshot`.
3. **Programmatic provenance extraction.** `JdbcProvenanceService` implements `ProvenanceService`. It discovers primary keys through `DatabaseMetaData`, reads IDs directly from result rows, and creates `ProvenanceRecord(table, recordId, fieldsUsed)`. Aggregate queries identify contributing source records.
4. **Answer synthesis.** `AnswerSynthesisService` is another `@AiService`. Its structured `AnswerDecision` contains only `answer` and is instructed to use only the supplied rows.
5. **HTTP response.** `QueryController` maps `POST /api/v1/query` to `QaEngineService` on Micronaut’s blocking executor and returns `QueryResponse`.

## Configuration

The active file is `src/main/resources/application.conf`, not YAML:

```hocon
datasources {
    default {
        driver-class-name="org.h2.Driver"
        url="jdbc:h2:mem:bloompath;DB_CLOSE_DELAY=-1"
        username="sa"
        password="password"
    }
}
micronaut.application.name=bloompath
langchain4j.ollama {
    base-url = "${OLLAMA_BASE_URL:`http://localhost:11434`}"
    model-name = "gemma4:e4b-mlx"
    streaming-chat-model.response-format = "json_object"
    streaming-chat-model.timeout = 2m
    streaming-chat-model.log-requests = true
    streaming-chat-model.log-responses = true
}
```

`OLLAMA_BASE_URL` is the only environment-variable binding in the main configuration, defaulting to `http://localhost:11434`. H2 is in-memory with `DB_CLOSE_DELAY=-1`. `DatabaseInitializer` loads `/schema.sql` once on `StartupEvent`.

## Domain Rules & Data Model

`src/main/resources/schema.sql` defines:

| Table | Primary key | Purpose |
|---|---|---|
| `clients` | `client_id` | Client identity, name, date of birth, creation timestamp |
| `programs` | `program_id` | Program name and description |
| `staff` | `staff_id` | Staff identity, role, email |
| `case_statuses` | `status_id` | Client/program case, optional staff assignment, status, update time |
| `service_activities` | `activity_id` | Dated client/program/staff activity, notes, flag state |

Foreign keys connect case statuses to clients, programs, and optional staff; activities connect to all three corresponding entities. `case_statuses.status` is constrained to exactly `Active`, `On Hold`, `Pending Review`, or `Completed`.

Active cases or active-client queries must join/filter `case_statuses` with `status = 'Active'`. For counts of clients by status, the intent prompt requires joining clients to case statuses and counting `DISTINCT clients.client_id`; case rows are counted only when the question asks for cases.

Seed data contains five clients, three programs, three staff members, seven case-status rows, and seven activities. The ambiguity data is John Doe (`CLI-101`) and John Smith (`CLI-105`).

## Local Setup & Running Instructions

Prerequisites:

- Java SDK 25;
- the Gradle wrapper (Gradle 9.6.1);
- ollama `gemma4:e4b-mlx`, defaulting to `http://localhost:11434`.

There is no `OPENAI_API_KEY` configuration in this repository. Set the Ollama endpoint when needed:

```bash
export OLLAMA_BASE_URL="http://localhost:11434"
```

Run the service:

```bash
./gradlew run
```

Run tests:

```bash
./gradlew test
```

Tests use `jdbc:h2:mem:bloompath-test;DB_CLOSE_DELAY=-1` and a three-minute Micronaut HTTP client read timeout.

## API Reference & Test Scenario Coverage

### DTO shapes

Request:

```json
{"question":"How many active cases are assigned to Sarah Jenkins in Youth Outreach?"}
```

`QueryRequest` contains only `question: String`. A response has this shape:

```json
{
  "status": "SUCCESS",
  "question": "How many active cases are assigned to Sarah Jenkins in Youth Outreach?",
  "answer": "...",
  "provenance": [
    {
      "table": "case_statuses",
      "recordId": "CAS-001",
      "fieldsUsed": ["status_id", "client_id", "program_id", "assigned_staff_id", "status", "updated_at"]
    }
  ],
  "clarificationPrompt": null
}
```

`QueryStatus` is `SUCCESS`, `AMBIGUOUS`, or `REFUSED`. `ProvenanceRecord` contains `table`, `recordId`, and `fieldsUsed`. `clarificationPrompt` is nullable. The model synthesizes answer text, so tests assert properties rather than one complete answer string.

### Five controller scenarios

1. **Aggregation / metrics**

   Request: `How many active cases are assigned to Sarah Jenkins in Youth Outreach?`. `testMetricQuery` expects HTTP 200, `SUCCESS`, and non-empty provenance. Seed rows `CAS-001` and `CAS-002` are the contributing active Youth Outreach cases assigned to Sarah Jenkins.

2. **Temporal / history**

   Request: `What was the last service activity recorded for Client CLI-101?`. `testTemporalQuery` expects HTTP 200, `SUCCESS`, and an answer containing `Follow-up`. The latest seeded activity is `ACT-002` at `2026-01-20 15:30:00`.

3. **Cross-entity filtering**

   Request: `List all clients in Housing Support who have flagged or uncompleted notes?`. `testCrossEntityQuery` expects HTTP 200, `SUCCESS`, and provenance containing `CLI-103`. Flagged activities use `is_flagged = TRUE`.

4. **Ambiguity resolution**

   Request: `What was John's last activity?`. `testAmbiguousQuery` expects HTTP 200, `AMBIGUOUS`, and a non-null clarification prompt. The matching clients are John Doe (`CLI-101`) and John Smith (`CLI-105`); no provenance is added.

5. **Out-of-scope refusal**

   Request: `What is the annual operating budget for Housing Support?`. `testRefusalQuery` expects HTTP 200, `REFUSED`, and no provenance. The fallback answer is:

```json
{
  "status": "REFUSED",
  "question": "What is the annual operating budget for Housing Support?",
  "answer": "I cannot answer this question. Financial and budget data are not tracked in BloomPath operational records.",
  "provenance": [],
  "clarificationPrompt": null
}
```

These are Micronaut HTTP integration tests using the real injected client, controller, services, H2 database, and configured AI services. `QueryControllerTest.kt` defines no mocks or mock setups.

## Technical Trade-offs & Key Decisions

**Deterministic SQL parsing vs. free-form agent execution.** Returning one read-only parameterized query improves predictability, auditability, SQL-injection resistance, and schema guardrails. It is less flexible than an open-ended agent and requires prompt/schema evolution for new question types.

**Programmatic provenance vs. LLM-derived citations.** JDBC metadata and primary-key values guarantee that cited IDs correspond to database records. The trade-off is extra handling for aliases, aggregates, and metadata; the answer model cannot invent provenance but also cannot explain anything absent from supplied rows.

**In-memory H2 vs. production RDBMS / vector DB.** H2 makes the PoC self-contained and repeatable, but data disappears with the JVM and production concurrency/operations differ. No vector database or embedding retrieval is implemented. Production would need durable storage, migrations, secrets, observability, query-policy enforcement, and any separately justified semantic index.
